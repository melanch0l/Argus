# PostgreSQL-only Phase 2 foundation

User approval replaces the historical SQLite choice with **PostgreSQL 17**.
This is deployment scaffolding only: no agent, backend, frontend, Docker socket,
privileged container, SQL schema, migration, repository, application role or
functional API is deployed here. Phase 7 owns database/REST implementation and
its reviewed migrations. The privileged agent remains separate host software.

## Verified image pin

On **2026-11-02**, Docker Hub official `library/postgres` tag metadata reported
`17.11` as the highest exact `17.x` patch tag. The Docker Registry manifest
response independently confirmed the multi-platform OCI index digest:

```text
postgres:17.11@sha256:3b0cda93be7c8dba2ed484d19393d93845dc3dafb88973e248ba8e6d99d784e1
```

The index contains Linux amd64 and arm64/v8 images, among other platforms.
This is an index digest, not an invented architecture-specific image digest.
Metadata sources:

- <https://hub.docker.com/v2/repositories/library/postgres/tags?page_size=100&name=17.>
- `https://registry-1.docker.io/v2/library/postgres/manifests/17.11` (bearer-token
  authenticated request; verified `Docker-Content-Digest` response header).

No image was pulled or run on the development host: Docker is absent. Metadata
verification does not establish image runtime behavior, extension compatibility,
or a vulnerability-free image. The digest is intentionally fixed: tag changes
will not automatically deliver security patches.

## Local operator setup (not executed here)

Install Docker Engine and a current Docker Compose v2 on the intended host.
Run the following from the repository root, **only when ready to start a local
database**. Create a real secret outside the checkout; never commit it, place it
in `.env`, paste it into a command argument, or print it to logs:

```sh
install -d -m 700 ~/.config/argus
(umask 077; set -C; openssl rand -hex 32 > ~/.config/argus/postgres-password)
realpath ~/.config/argus/postgres-password
cp -n deploy/.env.example deploy/.env
```

The generation command refuses to overwrite an existing password file. Protect
that file as mode `0600` and its directory as `0700`; keep it on an appropriately
protected filesystem. Edit `deploy/.env` so `POSTGRES_PASSWORD_SECRET_FILE` is the
absolute path printed by `realpath`. `.env.example` contains only a non-secret
placeholder path. Compose refuses an unset or empty path, and the source file
must exist. No actual secret is supplied or generated by this scaffold.

```sh
docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d --wait --wait-timeout 90 postgres
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
```

These commands download an image and start a persistent service; they are
operator instructions, not commands run by CI or by this implementation task.
Compose file-backed secrets are protected host files mounted read-only at
`/run/secrets/postgres_password`, **not** an encrypted secret vault. Keep Docker
access restricted. The official entrypoint reads `POSTGRES_PASSWORD_FILE`; no
literal password or `POSTGRES_PASSWORD` value appears in the Compose environment.

The only host port is **127.0.0.1:5432**. Do not change to `0.0.0.0`, forward it,
or treat loopback as authorization. Loopback publication does not isolate the
container from other containers on its Docker network or from host admins.
There is no production TLS setup; remote deployment requires reviewed TLS and
`verify-full` clients. This is a local foundation, not production-ready storage.

`pg_isready` checks whether PostgreSQL accepts connections; it does **not** prove
password correctness, application authorization, durability, schema readiness
or successful migrations. Validate actual password authentication separately
with an interactive password prompt (`psql -W`), never a password in a URI/CLI
argument. For example, from a host with the PostgreSQL client installed:

```sh
psql -h 127.0.0.1 -p 5432 -U argus_bootstrap_admin -d argus -W -c 'SELECT version();'
```

## Persistence, privileges and resource limits

- PostgreSQL 17 uses the named volume `postgres_data` at
  `/var/lib/postgresql/data`. Do not apply PostgreSQL 18's different volume
  layout. `docker compose down` retains data; `down -v` **destroys** the volume.
- `POSTGRES_USER=argus_bootstrap_admin` creates the official image's bootstrap
  **superuser administrator**, NOT a least-privileged future backend login.
  Never give these credentials to a backend or browser. No application exists
  in this Compose project.
- `POSTGRES_*` bootstrap settings apply only to an empty data directory. Updating
  the password file does not rotate the password of an existing database. Plan
  coordinated SQL credential rotation and a protected backup; do not delete a
  volume to solve an authentication mismatch.
- The command explicitly enables `fsync`, `full_page_writes`,
  `synchronous_commit` and SCRAM password encryption. These are configuration
  intentions until inspected on a running database (`SHOW ...`); underlying
  storage and backup/restore still need actual durability validation.
- Foundation limits: 1 CPU, 512 MiB memory, 128 PIDs, 128 MiB shared memory,
  30 connections, bounded memory settings, 30 s statement and 60 s idle-in-
  transaction timeouts, two autovacuum workers and rotating container logs.
  These are conservative starting settings, not measured capacity budgets.
  PostgreSQL process limits/timeout choices must be validated under actual load.
- `max_wal_size=512MB` is a **soft checkpoint target**, not a hard disk/WAL cap;
  `max_slot_wal_keep_size=256MB` is also not an immediate quota. A named volume
  has no hard disk bound here. Before nontrivial ingestion, provide filesystem
  capacity/quota, free-space monitoring, WAL/replication-slot monitoring, tested
  retention/vacuum and admission backpressure. Do not claim bounded disk use.

## Phase 7 prerequisites (not implemented)

Create separately reviewed migration and non-superuser application roles using
migrations, grant only required schema/table/sequence privileges, revoke unsafe
public defaults, and test negative permissions. Pin a compatible `pgx/v5`
version in that phase; no driver dependency or pretend database repository is
introduced here.

The Phase 7 implementation must follow the architecture contracts: parameterized
queries; `READ COMMITTED`; per-host row locks and separately locked global rule
publication; unique/FK constraints and race-safe immutable idempotency; bounded
transaction/deadlock retries, pools, admission, retention and indexed keyset
pagination. Preserve UUIDs, checked `NUMERIC(20,0)` uint64 values, unchanged wire
decimal strings, exact nanoseconds alongside microsecond `timestamptz`, and
canonical JSON bytes/text separately from JSONB projections. Preserve evidence,
epochs and lifecycle semantics. None of these properties is delivered by merely
starting this image.

Require authenticated application access, remote `verify-full` TLS, operational
disk/WAL/vacuum/pool budgets, least-privileged credentials, and a **tested**
`pg_dump`/restore runbook before storage acceptance. Physical PITR is a separately
reviewed optional addition. No backup, restore, SQL or migration test has run as
part of this foundation.

## Security updates and re-pinning

Review PostgreSQL 17 patch releases and base-image advisories regularly. Resolve
the official exact patch tag through Hub and Registry, compare the index digest
and supported platforms, review release notes and image scanning results, then
update the tag **and** digest together in `compose.yaml` and this record. Test
Compose rendering, password handling, startup/health, retained-volume upgrade,
durability settings and backup/restore on the actual host before rollout. Even
if the patch number is unchanged, base-image security rebuilds require a new
digest and review. Do not silently replace the pin with `postgres:17`, `latest`
or an unverified digest. Major-version upgrades require a separate migration
plan and are not accomplished by changing the image tag.
