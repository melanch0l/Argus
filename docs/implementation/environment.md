## Ubuntu 24.04 verification procedure — not run

Use an authorized real Ubuntu host/VM with its own kernel and rootful Docker. An ordinary workload container or Docker Desktop VM from macOS is not substitute host evidence. Record installed package versions and effective service permissions; do not silently disable lockdown, LSM, unprivileged-BPF restrictions or other security controls.

1. Verify `/etc/os-release`, `uname -r`, architecture and the intended local Docker daemon. Inspect apt package candidates before installing; Clang/LLVM 18 is a candidate family, not an exact tested pin. Typical package requirements include Clang/LLVM with BPF backend, make, bpftool/Linux tools matching the running kernel, CA certificates, Git, rootful Docker Engine/Compose v2 and PostgreSQL 17 client tools. Distribution packaging/repository configuration must be reviewed on the actual host; no installation has run here.
2. Install the reviewed Go/Node/npm versions, check upstream security advisories and update old patch baselines before deployment. Record exact package/tool versions and binary provenance. Ensure root's trusted PATH can locate required tools before privileged inspection; do not blindly preserve an untrusted developer PATH under sudo.
3. Build unprivileged (`make deps build`), inspect the source/binary, then run read-only inspection (`make envcheck`). No privileged probe runs by default. Reports include BTF readability, cgroup2 mount/controllers, hook format-file discovery, lockdown/LSM where readable, tool versions, llc BPF targets and Docker selection.
4. When explicitly authorized, request transient feature probing on that target:

```sh
mkdir -p reports
(umask 077; sudo ./bin/argus-envcheck --privileged --strict > reports/environment-ubuntu.json)
```

`--privileged` allows bounded `bpftool -j feature probe kernel`, which performs temporary kernel capability tests. It does not load project monitoring programs, attach hooks, disable policy, mount filesystems or alter sysctls. It requires Linux and effective UID 0; root alone may still be blocked by policy. Each command has a five-second timeout and bounded output. Rootless, remote/unmatched Docker, unsupported/missing evidence, timeout or permission failures must remain visible. Output capture/encoding errors are nonzero, not a pass.

5. Strict requirements include actual Ubuntu 24.04 and supported architecture; readable BTF/cgroup v2/critical execution tracepoint; required tool commands and frontend engine ranges; llc BPF target; Docker version/rootful/cgroup v2 evidence; local endpoint and daemon/host consistency; explicit tracepoint/cgroup-skb, ringbuf-map and per-program ring-buffer-helper feature evidence. Currently the endpoint must be exactly `unix:///var/run/docker.sock` with no `DOCKER_HOST`/`DOCKER_CONTEXT` override; ambiguous overrides are not accepted as host proof. Matching kernel/architecture establishes consistency, not cryptographic host identity. Reconcile unusual legitimate daemon configurations manually before changing the policy.
6. Examine all checks, not just the exit code. Hook filenames and successful generic feature probes do not establish intended-program verifier acceptance, attachment semantics or coverage. Those controlled workload tests remain Phase 3 and need separate approval. Record required unsupported features and seek an explicit compatibility decision rather than changing their status to pass.

Follow the [deployment runbook](../../deploy/README.md) for an operator-created protected password file and database-only Compose.
